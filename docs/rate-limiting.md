# API送信制限の運用

`server/game.mjs` は `server/rate-limit.mjs` によって送信回数を検査します。Cookieの形式、進捗バージョン、APIのJSON形式は変更していません。既存の進捗を維持するため、この修正だけで署名鍵や `progressVersion` を変える必要はありません。

## 制限と保存内容

| 対象                           | 上限            | 保存期限                |
| ------------------------------ | --------------- | ----------------------- |
| 同じIPの全API通信              | 600回 / 60秒    | 最初の通信から60秒      |
| 同じIPの有効な回答送信         | 120回 / 60秒    | 最初の回答から60秒      |
| 同じセッションの有効な回答送信 | 1回 / 750ミリ秒 | 最初の回答から750ミリ秒 |

固定窓方式です。窓の境界では短時間に上限の約２倍を処理し得ます。超過した通信も窓内の回数に含め、429と秒単位の `Retry-After` を返します。上限値は `rate-limit.mjs` にあります。共用回線の参加者はIP枠を共有するため、イベントの人数・実際の操作回数に合わせて調整してください。分散した多数のIPによる攻撃や費用全体を抑えるにはWAF・予算通知も必要です。

本番の共有ストアはUpstash Redis REST APIに対応しています。キーは署名鍵でHMAC化したIPまたはセッションIDと用途の組合せ、値は回数です。Luaの `EVAL` 内で `INCR`・`PEXPIRE`・`PTTL` を実行し、複数のFunctionでも同じキーを使って原子的に加算します。答え、進捗、生のIP、Cookie本文はRedisへ送りません。HMAC化した識別子も運用データとして保管先・権限を管理してください。

ローカルではソケットのIP、本番Vercelではプラットフォームが設定する `x-forwarded-for` を使います。ローカルで任意の転送ヘッダーを送ってもIP枠は変わりません。外部リバースプロキシを追加するときは、この信頼境界を再検証してください。[Vercelのリクエストヘッダー仕様](https://vercel.com/docs/headers/request-headers)

## 本番へ導入する順序

1. 対象Vercelプロジェクト用のUpstash Redisを用意します。検証用と本番用を分け、既存の別用途のDBを流用しないでください。地域・契約・費用は運用主体で決めます。
2. 各環境のサーバー用環境変数に `UPSTASH_REDIS_REST_URL`（HTTPS）と `UPSTASH_REDIS_REST_TOKEN`（書込可能なトークン）を設定します。`CTF_SESSION_SECRET` は既存の値を維持します。秘密値をリポジトリ・報告書・チャットへ貼り付けないでください。
3. トークンには `EVAL` とスクリプト内で使用するコマンドの実行権限が必要です。専用DBと最小限の権限を使い、URLへのユーザー名・パスワード埋め込みは行いません。[Upstash REST API仕様](https://upstash.com/docs/redis/features/restapi)
4. ローカルで `npm test`・`npm run check`・`npm run build` を実行します。ブラウザ検査はローカルサーバー起動後に `npm run test:browser-security` を実行します。自動テストの共有REST経路は模擬応答であり、実サービスへの接続確認とは別です。
5. 検証用Vercel環境でビルド・起動を確認し、同じCookieの回答を直後に再送して429と `Retry-After` を確認します。750ミリ秒後の成功、ヒント・解説・復元・リセットも確認します。大量通信は本番で試さないでください。
6. 検証した版を本番に反映し、GET・回答・進捗復元と503の有無を確認します。Redisの使用量・遅延・429件数・ホスティング費用を監視します。

`VERCEL` が設定されている場合、または `NODE_ENV=production` の場合、共有ストアなしのビルドは失敗します。設定を省略した新しい版が、正常な既存Deploymentを置き換えることを防ぐためです。URL形式と設定の有無を検査するもので、接続・権限・残容量まではビルド時に検証しません。

実行時の接続期限は１回３秒です。共有ストアの失敗・不正な応答・信頼できるIPが取得できない場合は503になり、制限なしでの処理に切り替わりません。回答では全通信枠と回答枠の２回ストアに接続します。ブラウザの12秒期限と合わせ、実際の遅延も検証してください。障害時はRedisの稼働・設定を復旧し、必要なら確認済みの版へ戻します。

`CTF_PUBLIC_ORIGIN` は任意です。独自の配信経路で必要な場合に `https://ctf.example` のように公開Originを設定します。未設定時は、VercelではHTTPSと実際のHost、ローカルではソケットのTLS状態とHostから比較先を作ります。複数のPreview URLを使う環境へ本番のOriginを固定しないでください。

2026-10-17、対象プロジェクト `cyber-first-step-ctf` で以下を下書き保存し、条件を読み直して確認しました。本番へは未公開です。

| 項目         | 内容                               |
| ------------ | ---------------------------------- |
| ルール名     | `CTF API request rate`             |
| ID           | `rule_ctf_api_request_rate_tDVw2X` |
| パス         | `/api/game` と完全一致             |
| 算法・集計   | 固定窓60秒、600回、IP単位          |
| 超過時の動作 | Log（記録のみ、遮断しない）        |

[変更の確認画面](https://vercel.com/yukipotetos-projects/cyber-first-step-ctf/firewall/rules)で差分を確認し、運用担当者が公開します。その後、[対象ルールの通信状況](https://vercel.com/yukipotetos-projects/cyber-first-step-ctf/firewall/traffic?filter=rule_ctf_api_request_rate_tDVw2X)で共用回線を含む正常な利用が該当していないか確認します。検証環境で遮断を試してから本番の429へ移行します。WAFのカウンターはリージョンごとであり、共有Redisの全体カウンターとは集計範囲が異なります。[Vercelのレート制限仕様](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)

この下書きは現時点の攻撃防止機能として数えません。共有Redisの準備・実接続検証・再デプロイも未完了です。既存本番の署名鍵やデータベースへの接続は変更していません。

## 進捗の再送について

今回サーバー側へ移したのは送信頻度の判断です。過去の正しい署名付きCookieによる進捗の巻き戻しや延べイベントの重複を完全には防ぎません。現行の進捗は自己学習用で、人数や試験の厳密な証明には使えません。旧Cookieの失効や厳密な記録が必要になった場合は、別途サーバー側に進捗の最新版を保存する設計が必要です。
