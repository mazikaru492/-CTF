## F-01：署名付きCookieの再送による頻度制限の回避

**重要度：中程度。分類：CWE-799 / OWASP API4:2023。**

### 根拠

[server/game.mjs](../server/game.mjs) の `decodeState()`（24〜58行）は署名・期限・データ形式を検証しますが、Cookieが最新かどうかは検証しません。`handler()` の187〜191行は、そのCookie内の `last` と現在時刻を比較して750ミリ秒の制限を判断しています。

署名は値の改ざんを検知しますが、過去に発行された正しい値の再送を防ぎません。攻撃側は秘密鍵を知る必要がなく、自分で取得したCookieを保存するだけで再現できます。

### 再現結果

1. `GET /api/game` で初期Cookie `C0` を取得します。
2. `C0` を付けて `{"action":"answer","id":1,"answer":"AUDIT_INCORRECT"}` を送信します。HTTP 200と更新Cookie `C1` が返ります。
3. 直後に最新の `C1` を使うと429になります。
4. 同じリクエストを、保存しておいた `C0` を使い続けて送信すると、制限期間内でも200になります。

| 検証                                     | 観測結果                |
| ---------------------------------------- | ----------------------- |
| ハンドラー：最新Cookieによる直後の回答   | 429                     |
| ハンドラー：保存Cookieによる４回の回答   | １ミリ秒の間に200を４回 |
| ローカルHTTP：保存Cookieによる３回の回答 | 11ミリ秒の間に200を３回 |

新しいCookieを取得し直す操作さえ不要です。GETや他の操作にも共通のサーバー側カウンターは、今回確認した実装にはありません。本番ホスティング側の制限の有無は未確認です。

### 影響

アプリ内の回答頻度制限を、自動アクセスに対する防御として利用できません。アクセス増加による処理量・転送量・ログ量・費用の増加が懸念されます。ただし、大量送信は実施しておらず、本番のサービス停止や費用増大は実証していません。

同じ「古い正しい状態を受け付ける」性質により、以下も確認できました。同一原因から生じる関連事項として扱い、別の脆弱性として重複計上していません。

- `official` を同じ初期Cookieで３回送ると、`official_click` が３件記録されました。
- 解説を取得した後、解説取得前のCookieで答えを送ると、「解説で学習」ではなく自力の正解として記録できました。既存のテストは最新Cookieを引き継ぐ経路を確認しており、この経路を検知しません。
- リセット前の進捗Cookieを保存していれば、リセット後もそのCookieで以前の進捗を取得できました。リセットは新規状態への置換で、旧Cookieの失効処理ではありません。

他人のCookieの取得や、他人の進捗へのアクセスは実証していません。個人情報やアカウントを扱わない現行用途では影響は限定されますが、正解数・クリック数を厳密な評価指標として利用する用途には適しません。

### 対策

1. 公開APIの入口で、Cookieを更新・削除しても回避できない頻度制限を実施します。ホスティング側のWAF等、または共有ストアを使うサーバー側カウンターが候補です。IP等の判断材料は信頼できる配信経路から取得し、共用回線からの正常利用も考慮して閾値を決めます。
2. サーバーレスの各インスタンス内のメモリーだけに保存する制限は避け、GETと各POST操作も含めて利用量を制御します。Cookie内の `last` は操作補助として扱います。
3. 厳密な受講記録・イベント重複排除・旧状態の失効が必要なら、サーバー側で進捗の最新版とイベントを管理します。署名方式の変更だけでは、過去の有効なCookieの再送を解決できません。
4. 学習サイトとして現在の保存方式を維持する場合も、進捗は自己管理用、計測は延べ操作を含む近似値と位置づけます。

頻度制限・リソース上限・費用通知については [OWASP API4:2023](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/) が対策を整理しています。クライアントから状態を戻す設計の再送リスクについては [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) も参照してください。

## F-02：不正URLによるローカル開発サーバーの終了

**重要度：低。分類：CWE-248。**

### 根拠・再現結果

[scripts/dev.mjs](../scripts/dev.mjs) の34行で実行する `decodeURIComponent()` は、40行以降の `try/catch` の外にあります。

専用の開発サーバー子プロセスに `GET /%` を１回送ると、`URIError: URI malformed` が発生し、Node.jsプロセスが終了コード１で終了しました。そのプロセスが提供する画面とAPIの両方が利用できなくなります。

検証対象のNode.jsでは、未処理のPromise拒否を例外として扱うのが既定です。[Node.js v24.12.0の公式説明](https://nodejs.org/download/release/v24.12.0/docs/api/cli.html#--unhandled-rejectionsmode)を参照してください。

### 影響と対策

現行コードは `127.0.0.1` にだけ待ち受けるため、今回の評価はローカル環境の可用性に限定しています。Vercelの本番静的配信で同じ終了が起きるとは判断していません。

URLの解析とデコードをリクエスト単位の例外処理に含め、不正な表記には400を返します。修正後は `/%` や不完全なUTF-8エスケープへの応答と、その後も正常なGET・API呼び出しが継続できることを確認してください。

## 追加の注意事項

### 進捗・アクセス制御の設計

現行APIは匿名の公開教材用です。認証なしで問題・ヒント・解説を取得でき、解説には答えも含まれます。これは現在の画面・用途と一致しており、答えの漏えいや認証回避としては計上していません。職員限定の情報、個人別成績、試験の採点を追加する際には、本人確認・権限管理・サーバー側の記録を設計してください。

### Originとプロキシの信頼境界

- 通常の異なるホストのOriginと `Sec-Fetch-Site: cross-site` は403になりました。
- `Origin: null` は `new URL(origin)` が失敗し、400/403ではなく503になりました。実際の内部障害との区別を付けるため、Originの構文エラーを捕捉して4xxに分類することを推奨します。応答本文にスタックは露出しませんでした。
- `Origin` のホストが、リクエストの `x-forwarded-host` と一致すれば許可されました。これはそのヘッダーを任意に設定した直接検証の結果で、本番でブラウザのCSRFが成立することの証拠ではありません。本番入口がこのヘッダーを上書き・検証するかを確認し、必要なら設定済みの許可Originと比較してください。
- Originを持たない直接クライアントも利用できます。送信元の検査を本人確認として扱うことはできません。

### Content-Typeの厳密さ

136行の前方一致判定により、`application/jsonp` とJSON本文も200になりました。単独で情報漏えいやブラウザからの送信制限回避は実証していません。メディアタイプをパラメーターと分離し、`application/json` と一致するかで判断する方が明確です。

### Node.js本体とホスティング

監査環境は `v24.12.0` でした。2026年１月13日の [Node.js v24.13.0は複数の修正を含むセキュリティリリース](https://nodejs.org/en/blog/release/v24.13.0)であり、監査環境はそれより古い状態です。運用環境でサポートされるセキュリティ更新済みの24.xを使用してください。24.13.0が現在の最新版という意味ではありません。

本番で実際に使われるNode.jsのパッチバージョンは未確認です。各CVEがこのAPIから到達可能かも検証していないため、APIの悪用可能な高重要度の問題としては計上していません。`npm audit` の０件には、Node.js本体・OS・ホスティングの評価は含まれません。

## 対応の優先順位

1. 公開規模に応じた、Cookieから独立するAPI頻度制限と利用量・費用の監視を整えます。本番の既存WAF設定も確認します。
2. 進捗とイベント数を何に使用するかを決めます。厳密な成績・人数が必要なら、サーバー側の保存と重複排除を設計します。
3. 開発サーバーのURL例外処理、Originの構文エラー、Content-Typeの判定を修正します。
4. ローカルと本番のNode.jsパッチバージョンを確認・更新し、本番のCookie・ヘッダー・プロキシ動作を確認します。
